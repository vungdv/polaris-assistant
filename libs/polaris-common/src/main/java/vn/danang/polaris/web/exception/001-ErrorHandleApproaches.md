# Error Handling: Concepts Beyond Framework & Language

## 1. What "good" error handling actually means

Looking at the `GlobalExceptionHandler` you shared, it's already doing several things that go beyond "catch an exception, return a status code." Before comparing Spring-specific mechanisms, it's worth naming the underlying principles it's implementing — because these apply in any language, any framework, any protocol.

### 1.1 Error handling is an API contract, not an afterthought
A caller (a frontend, a mobile app, another service) needs to programmatically understand *what* went wrong, not just *that* something went wrong. This is why the code standardizes on **RFC 7807 (Problem Details)** — `type`, `title`, `status`, `detail` — instead of ad-hoc JSON shapes per endpoint. The contract is: every error, regardless of cause, looks the same shape on the wire.

### 1.2 Separate "detection" from "translation" from "presentation"
There are three distinct concerns that are easy to tangle together:
- **Detection** — the business/data layer decides something is wrong (e.g., stock is insufficient) and throws a domain-specific exception.
- **Translation** — a dedicated layer converts that internal signal into an external, protocol-appropriate response (HTTP status + structured body).
- **Presentation** — the client renders that into something a human or downstream system acts on.

The file you shared is entirely a **translation layer**. This separation means your domain code (`InsufficientStockException`, `DraftExpiredException`, etc.) never has to know anything about HTTP, JSON, or status codes — it just expresses business facts.

### 1.3 Errors should be actionable, not just descriptive
Notice the pattern repeated throughout: `remedy`, `actions`, `allowed_properties`, `invalid_param`. This reflects a principle sometimes called **"actionable errors"**: telling the caller *what happened* is necessary but not sufficient — a well-designed error also tells the caller (or its UI) *what to do next*. This is a UX and API-design discipline, independent of Spring.

### 1.4 Fail-fast vs. graceful degradation
Two different philosophies coexist here:
- **Fail-fast** (validation errors, bad pagination, type mismatches) — reject immediately with a precise diagnosis.
- **Graceful negotiation** (insufficient stock offering an "adjust quantity" action, or "search alternatives") — instead of a hard failure, the system offers a path forward. This is a deliberate design choice about how much the error-handling layer should try to help the caller recover versus simply reporting failure.

### 1.5 Error taxonomy and status code discipline
A mature error-handling strategy maps *causes* to *status code families* consistently:
- 4xx = the caller did something the API can't/won't fulfill as requested (client's responsibility to fix)
- 5xx = the server failed to do something it should have been able to do (server's responsibility)
- Within 4xx, further distinctions matter: 400 (malformed/invalid), 403 (authorization), 404 (missing), 409 (conflicting state — like the `IllegalStateException` → Conflict mapping here).

Getting this taxonomy right — and staying consistent — is a language-agnostic API design skill, not a framework feature.

### 1.6 Don't leak internals, but don't hide root causes from yourself
The handler carefully surfaces safe details (`invalid_param`, `received`, `allowed_properties`) while never leaking things like stack traces, SQL, or internal class names to the client. Internally, though, you still need logging/observability of the *real* exception for debugging — error handling for callers and error handling for operators are two different audiences with two different needs.

### 1.7 Fragility of string-matching on framework messages
The code has two explicit `TODO`s acknowledging it parses `InvalidDataAccessApiUsageException` and `IllegalArgumentException` messages via regex/`contains()` checks. This is a known anti-pattern: **coupling behavior to another library's internal, non-contractual error message text**. It works until a dependency upgrade rephrases the message, silently breaking your error translation. This is a general lesson: *typed exceptions are a contract; string messages are not.* Where possible, prefer catching a structural signal (a specific exception subtype, an error code, a field) over parsing prose.

### 1.8 Centralization vs. locality trade-off
Concentrating all translation logic in one place (as this file does) buys consistency and a single point of change, but it also means the file must know about every exception type in the system — it grows without bound and becomes a dependency magnet. This tension (one global authority vs. many local, context-aware handlers) is the central theme of the comparison table below.

## 2. Comparison of Exception-Handling Methods in Java Spring Boot

| Method | How it works | Upsides | Downsides | Best fit |
|---|---|---|---|---|
| **`@RestControllerAdvice` + `@ExceptionHandler`** (what your file uses) | A single `@RestControllerAdvice`-annotated class declares `@ExceptionHandler(SomeException.class)` methods; Spring intercepts exceptions thrown from *any* `@RestController` and routes them here. | • Centralized, DRY — one place to see all error mappings.<br>• Keeps controllers/services free of HTTP-specific code.<br>• Easy to enforce a consistent response shape (e.g. RFC 7807) app-wide.<br>• Testable in isolation. | • Becomes a large, growing "god class" as the app scales.<br>• Applies globally by default — harder to give one controller special-case behavior without extra guards (`@RestControllerAdvice(basePackages=...)` or `assignableTypes`).<br>• No access to fine-grained per-call context unless passed via the exception or request object. | Medium-to-large REST APIs that want one consistent error contract across all endpoints — the sweet spot for most services. |
| **Local `@ExceptionHandler` inside a single `@Controller`** | Same annotation, but declared as a method inside the controller class itself rather than an `@ControllerAdvice`. Only applies to that controller. | • Scoped, no risk of accidentally affecting unrelated endpoints.<br>• Good for one-off or controller-specific quirks. | • Duplicated logic if several controllers need similar handling.<br>• Easy to end up with inconsistent error shapes across the app.<br>• Doesn't scale as the number of controllers grows. | Small apps, prototypes, or a controller with genuinely unique error semantics that shouldn't be generalized. |
| **Inline `try/catch` in the method body** | Classic imperative handling — catch the exception where it happens and build the response right there. | • Maximum context — you know exactly what was being attempted.<br>• No "magic"/indirection; easy for newcomers to trace.<br>• Fine-grained control for a single tricky case. | • Not reusable — boilerplate multiplies across methods.<br>• Mixes business logic with HTTP/response-building concerns.<br>• High risk of inconsistent status codes/response shapes across the codebase.<br>• Harder to unit test business logic in isolation from HTTP concerns. | Rare, highly localized cases (e.g., a single endpoint needing a non-standard, one-off response) — not a general-purpose strategy. |
| **Extending `ResponseEntityExceptionHandler`** | Spring's built-in base class already handles many framework-level exceptions (`MethodArgumentNotValidException`, `HttpMessageNotReadableException`, etc.) via overridable `handleXxx()` methods; you subclass and override only what you need to customize, inside a `@ControllerAdvice`. | • Free, battle-tested handling for common Spring MVC exceptions.<br>• Consistent with what the framework already expects internally.<br>• Less code to write for standard cases. | • Tied to Spring MVC's exception taxonomy — less flexible for purely custom/domain exceptions.<br>• Overriding protected methods has a learning curve; signatures change across Spring versions.<br>• Can feel like fighting the framework if your error model diverges significantly from Spring's defaults. | Apps that want to customize/extend Spring's default MVC error handling rather than replace it wholesale. |
| **`HandlerExceptionResolver` (custom bean)** | Implement the `HandlerExceptionResolver` interface (or `AbstractHandlerExceptionResolver`) and register it as a bean; Spring calls it as part of the low-level dispatcher exception-resolution chain, before/alongside `@ExceptionHandler` resolution. | • Lowest-level control — runs early in the dispatch pipeline, can intercept exceptions `@ExceptionHandler` might miss (e.g., in interceptors/filters within the DispatcherServlet flow).<br>• Useful for cross-cutting infra concerns (metrics, generic fallback). | • Verbose, low-level API (`ModelAndView` return type feels dated for REST APIs).<br>• Poor ergonomics compared to annotation-driven style.<br>• Easy to accidentally shadow/conflict with `@ExceptionHandler` resolvers if resolver order isn't understood. | Framework/infrastructure-level concerns (e.g., a shared library adding baseline exception handling to many services) rather than everyday app-level error mapping. |
| **`@ResponseStatus` on the exception class itself** | Annotate a custom exception class directly, e.g. `@ResponseStatus(HttpStatus.NOT_FOUND) class ResourceNotFoundException extends RuntimeException`. Spring auto-maps thrown instances to that status with no handler method needed. | • Extremely low boilerplate — no separate handler class needed for simple cases.<br>• Status code lives right next to the exception definition — easy to find. | • Can't build a rich response body (no custom `remedy`, `actions`, structured fields like your `InsufficientStockException` needs).<br>• Couples the exception class to a web-layer concept (HTTP status), hurting reusability of that exception in non-web contexts (e.g., batch jobs, CLI tools).<br>• No central place to see the full error contract of the API. | Very simple services or internal tools where errors are minimal and don't need structured, actionable bodies. |
| **Servlet `Filter` — pre-`DispatcherServlet` error handling** | A `jakarta.servlet.Filter` wraps `doFilter()` in try/catch to catch exceptions that occur *outside* Spring MVC's dispatch (e.g., in other filters, or before the `DispatcherServlet` even routes to a controller). | • Only place that can catch truly early failures (auth filters, request-wrapping filters, etc.) that never reach `@ExceptionHandler`.<br>• Framework-agnostic — works even without Spring MVC. | • Can't easily use Spring's `ProblemDetail`/message-converter machinery — often has to write the response manually.<br>• Overlaps/duplicates responsibility with `@ExceptionHandler`; needs careful boundary-drawing to avoid double-handling.<br>• Less "Spring-idiomatic," so less discoverable by other developers. | Handling exceptions thrown by filters/security infrastructure *before* Spring MVC's own exception resolution ever runs. |
| **Spring Boot's `/error` `ErrorController` (whitelabel or custom)** | Spring Boot auto-forwards unhandled exceptions (that escape `DispatcherServlet` entirely) to `/error`, resolved by `BasicErrorController` or a custom `ErrorController` bean. | • Safety net — catches anything that slips through every other mechanism (e.g., container-level errors, filter chain issues).<br>• Guarantees callers never see a raw stack trace/HTML 500 page by default. | • Loses most contextual information by the time it's reached (harder to build rich, specific error bodies).<br>• Should be a last-resort fallback, not a primary strategy — overusing it means giving up on precise error semantics. | Final fallback/catch-all layer beneath `@RestControllerAdvice`, to guarantee no request ever returns an unstructured error. |
| **AOP-based handling (`@Aspect` + `@AfterThrowing`/around advice)** | An aspect intercepts method calls (often at the service layer) and reacts to thrown exceptions — logging, retry, transformation — via Spring AOP/AspectJ. | • Great for cross-cutting *non-response* concerns: logging, metrics, retry, circuit-breaking, auditing.<br>• Decouples infra concerns from both business logic and web layer. | • Not designed to *produce* HTTP responses — usually still needs to rethrow or delegate to `@ExceptionHandler` for the actual client-facing response.<br>• Proxy-based AOP has well-known limitations (self-invocation, final methods/classes, class-based vs interface-based proxying).<br>• Adds an extra layer of indirection that can make control flow harder to trace. | Observability/resilience concerns (logging every exception, triggering retries, incrementing error metrics) layered *alongside* one of the response-producing methods above — not a replacement for them. |

### Practical takeaway

These methods aren't mutually exclusive — mature Spring Boot services typically **layer** several of them:

1. **`@RestControllerAdvice`** (like your `GlobalExceptionHandler`) as the primary, centralized translation layer for domain and validation exceptions.
2. **`ResponseEntityExceptionHandler`** extension if you want to customize Spring's own built-in MVC exception handling rather than reinvent it.
3. **AOP** for logging/metrics/retry around exception-throwing code paths, orthogonal to how the response gets built.
4. **`ErrorController`/`/error`** as the last-resort safety net for anything that still escapes.
5. Inline `try/catch` and local `@ExceptionHandler` reserved for genuine one-offs, not as a general strategy.

The file you shared is a solid example of pattern #1 done well — RFC 7807 structure, actionable `remedy`/`actions` fields, and clear separation from domain code — with its main technical debt being the message-string-parsing `TODO`s in `handleInvalidDataAccessApiUsageException`/`handleIllegalArgumentException`, which is worth revisiting if a more structural way to detect those conditions becomes available (e.g., catching a more specific exception type upstream instead of parsing Spring Data's message text).
