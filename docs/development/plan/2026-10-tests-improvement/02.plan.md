# Tests Improvement: Plan

- **Scope:** give every automated test one declared purpose and a named, separately runnable stage, in every Maven module (`libs/*`, `apps/*`), plus the CI stages and the guideline that define them
- **Out of scope:** production code changes, new product features, speed mechanics (containers, forks, context caching: `test-speed.md`), the content of the telemetry contract test (`trace-improvement/aop-trace-improvement.md` O1)
- **Depends on:** [01.initial-idea.md](01.initial-idea.md), `Engineer-Guidelines.md` §4 · **Unblocks:** `test-speed.md` (re-sequenced in Q8)
- **Status:** Draft for review

## Goal

A developer can run the unit stage in seconds, the integration stage in minutes, and see which stage a test belongs to from its name alone. No JVM test asserts what k6 or e2e should (load, concurrency, time budget), and no integration test re-asserts business rules that a unit test owns. The test pyramid shape is measured on every build, so drift is visible.

## Technical Requirements

Each requirement is testable and covered by at least one slice. IDs are prefixed `TR-I` to match the references in `01.initial-idea.md`.

| ID | Requirement |
|:--|:--|
| TR-I1 | The guideline defines the scope × aspect matrix, the one-purpose rule, the naming/stage convention and the "push tests down" rule, and `Engineer-Guidelines.md` §4 links to it. |
| TR-I2 | Every existing test class is classified in an inventory by aspect (a row of the matrix) and by verdict: keep, move down, move to k6/e2e, merge, delete. Counts are re-measured. |
| TR-I3 | `*Test` means unit (no Spring context, no I/O) and `*IntegrationTest` means integration. The build runs them as two separate stages that can be invoked alone from Maven and `make`. |
| TR-I4 | A guard fails the build when a `*Test` boots a Spring context or opens a real boundary, or when an `*IntegrationTest` has no declared aspect. |
| TR-I5 | CI runs unit, integration, contract and e2e/perf as separate jobs, unit first and fail-fast. |
| TR-I6 | No JVM test asserts concurrency, ordering under load or a time budget. Each such check is either deleted or covered by a k6 scenario in `tests/perf`. |
| TR-I7 | Integration tests assert wiring only (mapping, query validity, HTTP contract, boundary behaviour). Every business rule they assert is covered by a unit test first, then removed from the integration test. |
| TR-I8 | Layer-crossing `@SpringBootTest` slices are limited to a small, named set of wiring smoke tests per app. |
| TR-I9 | Each build reports, per module, the count of unit, integration, contract and journey tests and the ratio between them. A threshold on the unit-to-integration ratio is agreed per module. |
| TR-I10 | Cross-context contracts (OpenAPI, CloudEvents) have their own contract stage that exercises provider and consumer without the full stack. |
| TR-I11 | Critical user journeys are a short, named list in the e2e stage, with no rule permutations. |
| TR-I12 | Cross-cutting aspects (AOP tracing) are unit-tested once on the aspect plus one wiring test, and not re-asserted in flow tests. |

### Q1: Taxonomy guideline and baseline inventory
**Covers:** TR-I1, TR-I2, TR-I12, SC-1. **Spec:** not yet written. **Depends on:** —
- Write the testing guideline from the matrix in `01.initial-idea.md` §3 and link it from `Engineer-Guidelines.md` §4 (which today defines tiers by tool, not by purpose).
- Re-measure the per-module counts and produce the inventory: each test class → aspect → verdict. The inventory feeds Q4 to Q7 and is not a task list by itself.
- Decide which already-known misplacements are the first targets, for example `OrderEventOrderingConcurrencyTest` and `AssistantTurnTimeBudgetIntegrationTest`.
- No code or build change.

### Q2: Separate unit and integration stages
**Covers:** TR-I3, SC-2, SC-4, D1. **Spec:** [q2 spec](../../specs/2026-10-tests-improvement/q2-separate-unit-integration-stages.md). **Depends on:** Q1
- Build-level change applied uniformly to all modules: the unit stage runs `*Test` only, the integration stage runs `*IntegrationTest` only, each invocable alone (Maven profile or phase, plus `make` targets).
- Rename or retag only what is needed to make the stages correct. Moving tests between layers belongs to Q5 to Q7.
- Observable outcome: `make test-unit` finishes without starting a container or Spring context.

### Q2.2: Convention guard and aspect declaration (ArchUnit)
**Covers:** TR-I4, SC-3, D2, D3. **Spec:** not yet written. **Depends on:** Q2
- Enforce the Q2 naming convention in the build, trying ArchUnit (rules as unit tests): a `*Test` must not boot a Spring context or open a real boundary; an `*IntegrationTest` must declare exactly one aspect.
- Decide and apply the aspect declaration mechanism (D2) and where the shared rules live without a new production dependency; existing untagged integration tests go in a frozen baseline that only shrinks (Q5 to Q7 tag them).
- The guard must not break builds that skip tests (Docker image builds use `-DskipTests`).

### Q3: Pyramid report in the build
**Covers:** TR-I9, SC-5, D4. **Spec:** not yet written. **Depends on:** Q2
- The build emits per-module counts and ratios in a machine-readable form and prints a short summary.
- Report only at first. A gate is introduced after Q7, with thresholds agreed per module.

### Q4: Move load, concurrency and time-budget checks to k6
**Covers:** TR-I6, D6. **Spec:** not yet written. **Depends on:** Q1
- Own bounded area: `tests/perf`. For each JVM test the inventory marks as concurrency, ordering-under-load or time-budget, add or extend a k6 scenario, or record why deletion is safe.
- Deleting the JVM originals happens in the module slice (Q5 to Q7), after the k6 scenario exists, so no risk is left uncovered between slices.

### Q5: `libs/polaris-outbox` conformance
**Covers:** TR-I7, TR-I8. **Spec:** not yet written. **Depends on:** Q2, Q2.2, Q4 (if it has concurrency checks)
- Pilot on the smallest module (19 test classes, 4 with `@SpringBootTest`) to validate the Q1 and Q2 conventions before the larger apps.
- Apply the inventory verdicts: push business rules down to unit tests, keep boundary integration tests (broker, DB), delete duplicates.
- Outcome: the module's unit stage is Spring-free and its integration tests each declare one aspect.

### Q6: `apps/polaris-assistant` conformance
**Covers:** TR-I7, TR-I8, TR-I6, TR-I12. **Spec:** not yet written. **Depends on:** Q2, Q2.2, Q4
- Same treatment as Q5 for 65 test classes (13 with `@SpringBootTest`, 12 named `*IntegrationTest`).
- Remove the time-budget and ordering assertions from the JVM suite once Q4 covers them.
- Telemetry assertions stay with the contract test owned by `aop-trace-improvement.md` O1; this slice only stops flow tests from re-asserting them.
- Coordinate with `assistant-turn-behaviour.md` (B1 turn catalogue) so the two plans do not move the same tests.

### Q7: `apps/polaris` conformance
**Covers:** TR-I7, TR-I8, TR-I6. **Spec:** not yet written. **Depends on:** Q2, Q2.2, Q4
- Same treatment as Q5 for 42 test classes (21 boot Spring), the module with the most inverted pyramid.
- Expect the largest number of rule-level assertions to move down into unit tests; the integration suite shrinks to persistence, web-slice and boundary tests plus a few wiring smoke tests.
- If the volume is too large for one reviewable change, split by internal seam (domain package), not by file count.

### Q8: Contract stage and journey list

- Define the short list of critical user journeys in the e2e stage, and move rule permutations out of it.
- May be split per bounded context if the contracts differ in tooling.

### Q9: CI stages and `test-speed.md` re-sequence

- Re-read `test-speed.md` against the new taxonomy, drop or re-order its items, and turn the Q3 report into a gate if D4 allows.

## Definition of Done

- [ ] Every slice is `done` and every TR maps to at least one passing check (a test, a build guard or a CI job).
- [ ] The guideline is linked from `Engineer-Guidelines.md` §4 and the inventory shows no open "move" verdicts.
- [ ] `make` has one target per stage and CI runs the same targets.
- [ ] No `*Test` boots Spring and no JVM test asserts concurrency or a time budget.
- [ ] The pyramid report is produced for every module on each build.
- [ ] Open Decisions are resolved or explicitly deferred.
