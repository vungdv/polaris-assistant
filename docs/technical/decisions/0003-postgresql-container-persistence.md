# ADR-0003: Architectural Strategy for Polaris Persistence: Transition from Embedded H2 to Dedicated PostgreSQL Container Database

* Status: Accepted
* Deciders: Polaris Architecture Team, Core Platform Engineering
* Date: 2026-09-09
* Technical Story: Transitioning the Polaris application container stack from embedded/file-backed H2 to an industry-standard, containerized PostgreSQL database service, ensuring strict domain boundary isolation from Keycloak IAM, dev-prod parity, and ANSI SQL forward migration compatibility.

---

## Context and Problem Statement

Initially, Polaris utilized an embedded/file-backed H2 database (`jdbc:h2:file:/app/data/polaris`) inside the application container for rapid prototyping and zero-dependency boot. 

However, running production or containerized development with embedded H2 presents severe architectural liabilities:
1. **Dev-Prod Parity Divergence ([AGENTS.md: Principle 1.4](../../../AGENTS.md)):** H2 dialect quirks (e.g., non-standard `DATEADD()`, permissive typing, non-locking semantics) mask database defects and create divergence from production relational databases.
2. **Container Ephemerality & Concurrency Limitations:** Embedded file-based H2 lacks robust connection concurrency, connection pooling resilience, and standard point-in-time recovery mechanisms.
3. **IAM vs Business Context Separation ([AGENTS.md: Principle 2.2](../../../AGENTS.md)):** The docker-compose environment already runs a PostgreSQL 16 container (`keycloak-postgres`) exclusively dedicated to Keycloak IAM. Polaris business data must not be conflated with identity infrastructure, nor should it remain on an in-memory toy engine.

How should Polaris architect its persistence layer in `docker-compose.yml` and application configuration to establish production-grade relational persistence while maintaining seamless local test execution and strict bounded context isolation?

---

## Decision Drivers

* **Dev-Prod Parity & Industry Standards ([AGENTS.md: Principle 1.1 & 1.4](../../../AGENTS.md)):** Align with PostgreSQL 16 as the lower-layer relational protocol and standard enterprise database.
* **Bounded Context Containment ([AGENTS.md: Principle 2.2](../../../AGENTS.md)):** Polaris business entities (`Catalog`, `Order`, `Customer`) must reside in an isolated operational database context, completely segregated from Keycloak IAM's internal authentication schemas.
* **Forward-Only Flyway Migration Compatibility ([AGENTS.md: Principle 1.4](../../../AGENTS.md)):** Flyway migration scripts must be strictly compliant with standard ANSI SQL (ISO/IEC 9075) so they execute flawlessly across both PostgreSQL and H2 test fixtures.
* **Resilience & Orchestration Health:** The application container must not boot or attempt schema migration until the relational database engine is ready to accept connections (`pg_isready`).
* **Zero Disruption to Automated CI/CD Testing:** Local unit and integration tests (`mvn test`) must continue to run rapidly in-memory or via standard test fixtures without requiring heavy external dependencies unless configured.

---

## Considered Options

* **Option 1: Colocate Polaris Database on Existing Keycloak PostgreSQL Container**
  - Connect Polaris to the existing `keycloak-postgres` container using a shared instance with either the same database or a secondary created database.
  - *Drawbacks:* Violates operational ownership and DDD context containment (AGENTS.md Principle 1.3 & 2.2). Blurs security boundaries (Keycloak credentials vs application credentials). Risk of Keycloak realm migrations/upgrades impacting business tables.
* **Option 2: Dedicated `polaris-db` PostgreSQL 16 Container Service (Selected)**
  - Introduce an independent `polaris-db` container service in `docker-compose.yml` using `postgres:16`, mounted on a named volume `polaris_db_data`, with dedicated healthcheck (`pg_isready -U polaris -d polaris`).
  - Configure Polaris application container to connect to `jdbc:postgresql://polaris-db:5432/polaris` with explicit dependency ordering (`polaris-db: condition: service_healthy`).
  - Add `org.postgresql:postgresql` driver and `org.flywaydb:flyway-database-postgresql` to `pom.xml`.
  - Standardize Flyway migration DDL/DML to ANSI SQL standard (`GENERATED BY DEFAULT AS IDENTITY`, `CURRENT_TIMESTAMP - INTERVAL '...'`).
* **Option 3: External Managed Cloud Database Only**
  - Discard containerized database and mandate connection to an external RDS/Cloud SQL instance.
  - *Drawbacks:* Destroys local offline developer ergonomics and self-contained docker-compose orchestration.

---

## Decision Outcome

Chosen Option: **Option 2: Dedicated `polaris-db` PostgreSQL 16 Container Service**.

### Key Architectural Specifications:

1. **Service Boundary Isolation:**
   - Define `polaris-db` in `docker-compose.yml`:
     ```yaml
     polaris-db:
       image: postgres:16
       container_name: polaris-postgres
       environment:
         POSTGRES_DB: polaris
         POSTGRES_USER: polaris
         POSTGRES_PASSWORD: polaris
       volumes:
         - polaris_db_data:/var/lib/postgresql/data
       networks:
         - polaris-net
       healthcheck:
         test: ["CMD-SHELL", "pg_isready -U polaris -d polaris"]
         interval: 5s
         timeout: 5s
         retries: 10
     ```
   - Declare persistent volume `polaris_db_data:` in root volumes.

2. **Application Configuration & Wiring:**
   - In `docker-compose.yml`, update `polaris` service environment:
     ```yaml
     SPRING_DATASOURCE_URL: jdbc:postgresql://polaris-db:5432/polaris
     SPRING_DATASOURCE_DRIVER_CLASS_NAME: org.postgresql.Driver
     SPRING_DATASOURCE_USERNAME: polaris
     SPRING_DATASOURCE_PASSWORD: polaris
     ```
   - Wire dependency orchestration:
     ```yaml
     depends_on:
       keycloak:
         condition: service_healthy
       otel-collector:
         condition: service_started
       polaris-db:
         condition: service_healthy
     ```

3. **Dependency Alignment (`pom.xml`):**
   - Enable PostgreSQL JDBC Driver:
     ```xml
     <dependency>
         <groupId>org.postgresql</groupId>
         <artifactId>postgresql</artifactId>
         <scope>runtime</scope>
     </dependency>
     ```
   - Add Flyway PostgreSQL Extension for Flyway 12+:
     ```xml
     <dependency>
         <groupId>org.flywaydb</groupId>
         <artifactId>flyway-database-postgresql</artifactId>
         <scope>runtime</scope>
     </dependency>
     ```

4. **ANSI SQL Standardization for Flyway Migrations:**
   - Primary key generation: Standardize `AUTO_INCREMENT` to standard `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` in `V1__init_schema.sql` and `V4__create_catalog_hierarchy_and_products.sql`.
   - Date arithmetic: Standardize H2-specific `DATEADD(...)` to standard SQL `CURRENT_TIMESTAMP - INTERVAL '1' HOUR` and `CURRENT_TIMESTAMP - INTERVAL '1' DAY` in `V2__seed_data.sql`.
   - This ensures dual compatibility: Flyway migrations execute identically and deterministically on both production PostgreSQL 16 and in-memory H2 test suites.

---

## Consequences & Verification

### Positive:
* True dev-prod parity conforming to AGENTS.md Principle 1.4.
* Clean bounded context separation between Keycloak IAM and Polaris domain persistence.
* Robust persistence across container recreation via named Docker volume `polaris_db_data`.
* Dual-compatible ANSI SQL migrations preserving blazing fast local test execution (`mvn test` 106/106 tests green).

### Negative / Operational Trade-offs:
* Requires an additional lightweight container (~30MB RAM) in the local Docker Compose stack.
